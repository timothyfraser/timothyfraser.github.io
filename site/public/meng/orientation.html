    How do you know it's working or failing?
    You often can't judge on expertise. So judge on evidence.
    1 · Before you build
    Say what success is.
    Checkably. "3,225 rows under 15 s" — not "it should be fast."
    2 · First
    Reproduce the failure.
    Watch it fail. Now you have a detector.
    3 · Measure
    Median of three.
    One timing is noise. And measure the right thing.
    4 · Verify
    From the far side.
    The live URL. The compiled PDF. Never the diff.
    5 · Adversarially
    Try to prove yourself wrong.
    An API that answers a nonsense request is not working.
    6 · Record
    Number, date, command.
    Unrecorded evidence evaporates in three weeks.
    Two sentences to keep
    "Looks right to me" is not evidence. And a green check mark is not a measurement of the thing you care about — it measures whatever someone decided to check.

    A new technique every week
    The tool you master now may be obsolete next fall. The transferable skill is telling what is real.
    Entering a new technique
    1
    Learn its vocabulary. Ten words unlock the docs
    2
    Run the smallest thing that runs
    3
    Break it deliberately. Errors teach the model
    4
    Find the real source of truth. Not a blog post
    5

    Real vs plausible — the tells
    It can invent a function signature, a config flag, or a benchmark it never ran. Each looks right.
    • A number with no provenance. Measured when, on what?
    • An API that's a little too convenient
    • "It should work now." Should is a forecast
    • Success with no command run. Scroll up
    The defence is the same each time: make it run, read the output.
    In a progress check
    Bring me the technique, not just the result. "Here's what I learned, what surprised me, how I verified it" beats a finished feature you can't explain.

    Appendix A1
    Pull request etiquette

    As the author

  • Keep it small. One idea per PR
  • Review your own diff first, adversarially
  • Green CI before asking for review
  • Reply to every comment — or say why not
  • Push fixes to the same branch
  • Flag what you're unsure about

    • As the reviewer

  • The code, never the person
  • Mark blocking vs optional — nit: or blocking:
  • Ask, don't assert, when unsure
  • Say what's good. It teaches the team
  • Don't bikeshed formatting. Use a linter
  • Review within a day
    • Not negotiable
    A PR that claims something must show the evidence.

    Appendix A2
    Secrets are hard to undo
    Committed then deleted is still in the history, and public repos are scanned by bots. The fix is rotation, not deletion.

    Do

  • Local .env, listed in .gitignore
  • Commit a .env.example — names, empty values
  • Runtime config on the server — Connect Vars, Actions secrets
  • Refer to keys by name in docs. Never by value
  • Tell me the same hour if you leak one. No embarrassment

    • Never

  • Never commit .env, a service-account JSON, a .pem
  • Never paste one into an issue, PR, or screenshot
  • Never print one in logs or a notebook cell
  • Never hardcode "just for testing"
  • Never put one in frontend code
    • Why the agent rules help
    Our repos make agents refuse to read .env files. An agent that can't read a secret can't paste one into a commit.

    Deploying to Posit Connect
    A Plumber API, end to end
    # from a gitignored .env
export CONNECT_SERVER=https://connect...
export CONNECT_API_KEY=...  # Publisher

# 1. describe the bundle — from REPO ROOT
Rscript -e 'rsconnect::writeManifest(
   appDir = "job/myjob",
   appPrimaryDoc = "plumber.R",
   appMode = "api")'

# 2. commit manifest.json

# 3. deploy
rsconnect deploy manifest job/myjob/manifest.json
    Five traps
    • .rscignore, not .rsignore
    • Connect's root is the app dir, not the repo root
    • Your .env isn't in the bundle. Use Connect Vars
    • A Viewer key 403s. So do stale credentials
    • A Var holds a value, not a file path
    Worth knowing
    A green merge is not a deploy.
    Confirm the workflow ran and passed. Then call the live URL. Rollback: Connect → Source Versions.

    Appendix A4
    Four times we believed a claim that was false
    All from these repos, this year. None caught by a test, a review, or a green check.
    1 · The merge that claimed otherwise
    The PR said the perf work survived. It hadn't.
    Re-measured: 28.4 s against a 15 s bar.
    Caught by: re-measuring, not reading the PR.
    2 · The optimization that never ran
    39× faster in the repo. The server ran the old one.
    A vendored copy nobody regenerated. 5.5 h of an 8 h nightly.
    Caught by: reading the deployed job log.
    3 · Two vintages in one document
    Figures from one run, table from another.
    Table 1 printed −2.68 beside figures at −1.68.
    Caught by: a person reading the compiled PDF.
    4 · The documentation was wrong
    A memory file described a filter never called.
    Disproved by arithmetic: 29,670 = 21,241 + 8,429.
    Caught by: checking the sum, not the paragraph.
    All four
    The written claim and the running system disagreed, and the claim was believed. Be the one who goes and looks.
